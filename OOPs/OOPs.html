Class

A Class is a user-defined data type that acts as a blueprint for creating objects. It encapsulates data and behavior together.

A class can contain fields, properties, methods, constructors, events, and other members.

Memory for instance data is allocated only when an object is created.

Class Memory

When you create the class only MetaData loads.

After creating the object then only Memory in Heap will be allocated.

Class contains

  • Fields
  • Properties
  • Constants
  • Methods
  • Constructors
  • Destructors (Finalizers)
  • Static Members
  • Nested Classes
  • Events
  • Indexers

Object

An object is an instance of a class, it represents a real-world entity and contains its own data (members or field) and behaviour (methods).

When you initialize the object using a new keyword, memory will be allocated in Heap.

Picture · how an object is stored in memory

Employee emp2 = new Employee(2) { Name = "Ravi" };

  1. The first time Employee is used, the CLR loads its metadata once. No object memory exists yet.
  2. new Employee(1) allocates a block on the heap big enough for the instance fields and runs the constructor.
  3. The variable emp1 (on the stack, if it is a local) stores only the address of that block.
  4. Methods are not copied into each object. Both objects share one copy of Work(); only the data is per object.
  5. When nothing references an object any more, the Garbage Collector frees it.
Correction

Value types are not "always on the stack". They live wherever their container lives. A local int sits on the stack, but the int _id field above lives inside the object on the heap.

Difference Between Class and Object

A class is a blueprint or template that defines the structure and behavior of objects. It specifies what data and methods objects will have but doesn't store instance-specific data. An object is an instance of a class created using the new keyword. Each object has its own memory and maintains its own state while sharing the same class definition.

ClassObject
Blueprint / templateInstance built from the blueprint
Declared onceCreated many times with new
Only metadata is loadedMemory allocated on the heap
Stores no instance dataHas its own state (field values)
Interview
Is string a value type?

No, it is a reference type. It is immutable, so every "change" creates a new string, which makes it behave like a value type when you assign and modify it.

02

Static

A static member belongs to the class itself, not to an object (instance).

Advantage is reusability. No data duplication.

Static members are stored in the static area (or Loader Heap).

Static field

A static member is a member belonging to a class rather than an instance of the class.

  • It is shared among the objects. So only one copy of this exists in memory.
  • A static member can access using the className without creating the object.

Example

Before:

Example · before 
public class Employee
{
    public string Name;
    public string Company = "Infosys";     // instance field
}

That means "Infosys" is duplicated in every object. Waste of memory.

Better Solution: Store it once.

Example · better solution 
public class Employee
{
    public string Name;
    public static string Company = "Infosys";   // one copy for the class
}

Console.WriteLine(Employee.Company);           // accessed with the class name
Static area · one copy
Employee (static)Company = "Infosys"
Heap · per object
Employee #1Name = "Asha" · no Company copy
Employee #2Name = "Ravi" · no Company copy

There is only one copy of: Company. No matter how many Employee objects you create.

Static Method

A static method belongs to the class rather than an instance. It can be called without creating an object and can directly access only static members of the class.

Note:

  • The static method can only access the static members. It can not access the non static member.
  • Only objects are able to access the non static method.
Correction

Precisely: a static method can't use instance members directly (it has no this). It can still use them through an object it receives or creates: static void Print(Employee e) => Console.WriteLine(e.Name);

Real-world Examples

Example 
Math.Max(10, 20);                    // utility, no state needed
Console.WriteLine("Hello");
string.IsNullOrEmpty(name);
int.Parse("42");

public class SalaryHelper
{
    public static decimal CalculateTax(decimal salary) => salary * 0.10m;
}
SalaryHelper.CalculateTax(50000);    // no SalaryHelper object needed

Static constructor

A static constructor can not have access modifiers. It is always Private implicitly. Compilers enforce this.

Usage of static constructor

To initialize the static field.

Example 
public class Employee
{
    public static string Company;

    static Employee()                 // no access modifier, no parameters
    {
        Company = "Infosys";
        Console.WriteLine("Static ctor ran");
    }

    public Employee() { Console.WriteLine("Instance ctor ran"); }
}

new Employee();   // Static ctor ran, Instance ctor ran
new Employee();   // Instance ctor ran   (static ctor does NOT run again)

Who calls the Static Constructor?

✅ CLR (Common Language Runtime).

The CLR automatically executes the static constructor. Exactly once.

Before:

  • First object creation
  • OR first static member access

Whichever happens first.

Also remember

A static constructor takes no parameters, can't be overloaded, and can't be called by your code.

Static Class

A static class is a class that cannot be instantiated and can contain only static members. It is commonly used for utility or helper functionality, such as the built-in Math class.

Interview
Why is Main() static?

So the CLR can call the entry point without first creating an object of the class.

Can we overload static methods?

Yes. Overloading only needs a different parameter list. Static methods cannot be overridden, though.

Inheritance

Inheritance is a feature of an OOP that allows one class to acquire members of another class.

It promotes code reusability, maintainability and extensibility.

Example 
public class Employee  { public string Name; public void Work() { } }
public class Manager   : Employee { public void ApproveLeave() { } }
public class Developer : Employee { public void WriteCode() { } }

Manager m = new Manager();
m.Name = "Asha";      // inherited from Employee
m.Work();             // inherited from Employee
m.ApproveLeave();     // its own

Note: The child class can not inherit the Private members static members and constructor.

Correction

Only constructors are truly not inherited. Private members are inherited (they exist inside the Manager object) but are not accessible from Manager's code. Public static members are reachable through the child too: Manager.Company works.

Why? The Diamond Problem

A
BDisplay() → "B"
CDisplay() → "C"
DDisplay() → "B" or "C"?

Why? If both B and C have a method named Display(), which one should D inherit? This ambiguity is called the Diamond Problem.

Example · how interfaces avoid it 
class B { public void Display() => Console.WriteLine("B"); }
class C { public void Display() => Console.WriteLine("C"); }
// class D : B, C { }          // ✗ not allowed in C#

interface IB { void Display(); }
interface IC { void Display(); }
class D : IB, IC               // ✓ interfaces are fine
{
    public void Display() => Console.WriteLine("D decides");
}

Interfaces only declare Display(); they don't bring two competing bodies. D writes the one implementation, so there is nothing to choose between.

Base

Base is a keyword that helps to access the members (constructors, methods, properties, fields) of the immediate parent class.

Calling parent constructor

base() is used to call the constructor of the base class.

Example 
public class Employee
{
    public int Id;
    public Employee(int id) { Id = id; Console.WriteLine("Employee ctor"); }
}

public class Developer : Employee
{
    public Developer() : base(101)
    {
        Console.WriteLine("Developer ctor");
    }
}

Before executing the Developer constructor, call the Employee(int id) constructor with the value 101.

A child constructor can call only its immediate parent's constructor.

Calling parent method

If the parent and child class have the same method. But I need to call the parent class method. In this time we need to use the base keyword call the parent method.

Example 
public class Employee  { public virtual void Work() => Console.WriteLine("Employee working"); }
public class Developer : Employee
{
    public override void Work()
    {
        base.Work();                               // Employee working
        Console.WriteLine("Developer writing code");
    }
}

Calling parent properties

Example 
public class Employee  { public string Title { get; set; } = "Employee"; }
public class Developer : Employee
{
    public new string Title { get; set; } = "Developer";
    public void Show() => Console.WriteLine($"{Title} / {base.Title}");  // Developer / Employee
}

Accessing the parent field

Example 
public class Employee  { protected decimal Bonus = 5000; }
public class Developer : Employee
{
    private new decimal Bonus = 8000;
    public void Show() => Console.WriteLine($"{Bonus} / {base.Bonus}");  // 8000 / 5000
}

No. Because base refers to the current object's base class. Static methods don't belong to an object; they belong to the class. Therefore, base is not available in a static context.

This()

This() is used to call the current class's other constructor.

For code reusability and maintainability.

Example 
public class Employee
{
    public int Id; public string Name; public string Dept;

    public Employee(int id, string name, string dept)
    { Id = id; Name = name; Dept = dept; }

A constructor can have only one constructor initializer either this(...) or base(...), not both.

Encapsulation

It is the process of binding the data and methods together to protect the data. While restricting the direct access to data. In C# We can implement this using the Private fields and public properties or methods.

Example 
public class Employee
{
    private decimal _salary;                       // hidden data

    public decimal Salary                          // controlled access
    {
        get => _salary;
        set
        {
            if (value < 0) throw new ArgumentException("Salary cannot be negative");
            _salary = value;
        }
    }
}

var e = new Employee();
e.Salary = 50000;      // ✓
e.Salary = -10;        // ✗ throws, the class protects its data
// e._salary = -10;    // ✗ compile error, private

Interview Tip

A common follow-up question is:

If auto-implemented properties are public (public int Age { get; set; }), is that encapsulation?

The answer is:

  • Technically yes, because access still goes through a property rather than a field.
  • However, it doesn't provide much protection because there's no validation or restricted access.
  • Stronger encapsulation uses private fields with validation logic in the property setter when business rules need to be enforced.
07

Abstraction

Abstraction is the process of hiding the implementation and showing the only essential functionality to the user. Abstraction is mainly achieved using the abstract and interface class.

Correction

An interface is not a class. Say "abstract classes and interfaces".

Advantage:

  • Hides complexity.
  • Improves maintainability.
  • Allows flexible implementations.
  • Lets users focus on functionality rather than implementation.

Interview Tip

Can we achieve Abstraction without using an abstract class?

Yes. We can achieve abstraction using interfaces as well. In fact, interfaces are often preferred when defining contracts because a class can implement multiple interfaces, whereas it can inherit from only one abstract class.

Does an abstract class have to contain an abstract method?

No. An abstract class can have zero or more abstract methods. Declaring a class as abstract simply means it cannot be instantiated directly.

Realtime Example and Advantage

Example · payroll 
public abstract class Employee
{
    public string Name;
    public abstract decimal CalculatePay();                  // WHAT, not HOW
    public void PrintPayslip() => Console.WriteLine($"{Name}: {CalculatePay()}");
}

public class Manager   : Employee { public override decimal CalculatePay() => 90000 + 15000; }
public class Developer : Employee { public override decimal CalculatePay() => 70000; }

public interface IReviewable { void Review(); }             // contract via interface

// var e = new Employee();   // ✗ abstract class can't be instantiated
Employee e = new Manager { Name = "Asha" };
e.PrintPayslip();          // payroll never knows how a Manager's pay is calculated

Advantage: payroll code calls CalculatePay() and stays the same when a new role is added.

08

Polymorphism

It is one of the four pillars of the OOPs, it allows the same method to behave differently based on the object by implementing the Method overloading (Compile-Time) and Method overriding (Run-Time).

Compile-Time polymorphism (Method overloading)

The compiler decides which method to call before the program runs. We can achieve this using the method overloading.

Method overloading is compile-time polymorphism. It means creating multiple methods with the same name in the same class but difference in the parameter list. The compiler decides which method to execute.

That's why it's also called as:

  • Compile-time Polymorphism
  • Static Polymorphism
  • Early Binding

Rules for Method Overloading

  1. Number of Parameters
  2. Type of Parameters
  3. Order of parameter
Example 
public class Payroll
{
    public void Pay(int id) { }                       // base version
    public void Pay(int id, decimal bonus) { }        // ✓ number of parameters
    public void Pay(string code) { }                  // ✓ type of parameters
    public void Pay(decimal bonus, int id) { }        // ✓ order of parameters
    // public int Pay(int id) { return 0; }           // ✗ return type alone: compile error
}
Add to the rules

Return type alone is not enough to overload. ref/out/in modifiers do count, but ref vs out alone does not.

Interview Tip

1. Can we overload static methods?

Answer

Yes. static int Add(int a, int b) and static double Add(double a, double b) can live together. Math.Max itself has many overloads.

2. Can constructors be overloaded?

Answer

Yes. Employee(), Employee(int id) and Employee(int id, string name) in one class is constructor overloading (see chapter 05).

3. Can methods be overloaded in different classes?

No. Method overloading is a concept within the same class.

Correction

Too strong. A derived class can add an overload of an inherited method: Employee.Work() plus Manager.Work(int hours), and both are callable on a Manager. Safer answer: "Normally within one class, but a derived class can add new overloads of inherited methods."

Method hiding

It is the process of hiding the child class implementation.

Correction

It's the other way round. The child declares a member with the same signature using new, which hides the parent's member. Which one runs is decided by the reference type at compile time.

Example 
public class Employee { public void Work() => Console.WriteLine("Employee works"); }
public class Manager : Employee
{
    public new void Work() => Console.WriteLine("Manager works");
    public void ApproveLeave() { }
}

Employee emp = new Manager();
emp.Work();              // Employee works
// emp.ApproveLeave();   // ✗ not visible through an Employee reference

See in this reference is Employee but the object is Manager.

So the compiler decides what all members access this emp reference.

For the reference emp type is employee. So only employee members are accessible.

Runtime Polymorphism

Runtime polymorphism is method overriding. It allows the child class to provide its own implementation that is already defined in the base class.

We can achieve this using the base method marked as "virtual" and the child method marked as "override".

At the runtime CLR decides which method should executes based on the object.

Method Overriding (Virtual, override)

Example 
public class Employee { public virtual  void Work() => Console.WriteLine("Employee works"); }
public class Manager : Employee
{                       public override void Work() => Console.WriteLine("Manager works"); }

Employee emp = new Manager();
emp.Work();              // Manager works

In this still reference type is Employee and object is Manager.

Now the CLR says and This decision happens at runtime:

The reference is Employee, but the actual object is Manager. I'll execute the Manager's overridden method.

First, the compiler checks whether the method is virtual. If it is virtual, the compiler generates a virtual call.

The Secret of calling different method

Picture · the method table (vtable)
Employee method table
slot: Work()→ Employee.Work
Manager method table
slot: Work()→ Manager.Work (override replaced the slot)
  1. Every object on the heap carries a pointer to its own type's method table.
  2. emp.Work() is a virtual call, so at runtime the CLR follows emp → object → Manager's table.
  3. The Work() slot there points at Manager.Work, so that runs. With new instead of override, Manager gets a separate slot and the Employee slot still points at Employee.Work.

Summary (hiding): Reference Type decides which method to call.

          

          

            
How the call is resolved (overriding)

            

              
1. Compile Time (Compiler)

                
emp is of type Employee
emp.Work();↓Compiler looks at Employee.Work()↓This method IS virtual↓Compiler generates VIRTUAL CALL (final decision in runtime)

              
2. Runtime (CLR)

                
CLR receives the virtual call↓Which object is emp pointing to?↓Manager↓Does Manager override Work()?
                  
YESCalls Manager.Work()
NOCalls Employee.Work()

            

            
Key point Decision is taken at RUNTIME based on ACTUAL OBJECT TYPE (Manager).

            
Summary (overriding): Actual Object decides which method to call.

Realtime Example and Advantage

      
Example · notifications

public class Notifier             { public virtual void Send(string msg) => Console.WriteLine("Log: " + msg); }
public class EmailNotifier : Notifier { public override void Send(string msg) { /* SMTP */ } }

}

        
Advantage: the caller is written once against the parent type. A new WhatsAppNotifier needs a new class only, with no change to NotifyAll.

Up-casting

      
It is the process of converting a child class object into parent class reference.

      
Instantiation

      
Example

Manager mgr  = new Manager();
Employee emp = mgr;                 // upcasting (implicit)

Employee emp2 = new Manager();      // most common form

      

      
Notes:

      
    
        
  • With this upcasting initialization, we can access only parent class members.
    • 
        
  • Up casting is safe.
    • 
      


      
Real life example

      
Think of a company. Your HR system stores everyone as an Employee.

      
Why? Because:

      
    
        
  • Developer is an Employee.
    • 
        
  • Tester is an Employee.
    • 
        
  • Manager is an Employee.
    • 
      

      
This is Upcasting.

      
Why is Upcasting So Important?

      
Without it, you'd have to write:

      
Example · without upcasting

List<Manager>   managers   = new();
List<Developer> developers = new();
List<Tester>    testers    = new();
// three lists, three loops, every time

      

      
Instead, you can write, and store all employee types together.

      
Example · with upcasting

List<Employee> employees = new()
{
    new Manager(), new Developer(), new Tester()
};

      

      
This is one of the biggest benefits of OOP.


      
Upcasting + Runtime Polymorphism

      
Example

Employee emp = new Manager();
emp.Work();          // Manager.Work() runs

      

      
Code Steps: Because:

      
    
        
  1. We performed Upcasting.
    2. 
        
  2. Work() is virtual.
    3. 
        
  3. The CLR checks the actual object.
    4. 
        
  4. The actual object is Manager.
    5. 
        
  5. It is called Manager.Work().
    6. 
      

      
This is Runtime Polymorphism in action.


      
Q1. Why do we use Upcasting?

      
We use Upcasting to write generic and reusable code. It enables runtime polymorphism, allows collections of base types to hold child objects, and is widely used in interfaces, dependency injection, and design patterns.

Down-casting

      
It is the process of converting the upcasted base class reference into child class reference.

      
Example

Employee emp = new Manager();     // upcast
Manager mgr  = (Manager)emp;      // downcast (explicit)

      

      
Notes:

      
    
        
  • The object will not be changed.
    • 
        
  • Only a new reference is created for this object. (check below image)
    • 
      

      
Memory Visualization

      
Picture

ApproveLeave() (Manager part, visible via mgr)

          

        

      

      
    
        
  • There is still only one object.
    • 
        
  • We're just creating another reference to the same object.
    • 
      

      
Now We Can Access Everything: (after down casting)

      
Example

mgr.Name = "Asha";     // ✓ Employee member
mgr.Work();            // ✓ Employee member
mgr.ApproveLeave();    // ✓ Manager member

      

      
Why is Upcasting safe but Downcasting unsafe?

      
Upcasting is always safe because every child object is also a parent object.

      
But downcasting is unsafe because not every parent object is a child object.

      
Example

Employee emp = new Developer();
Manager mgr  = (Manager)emp;      // ✗ runtime InvalidCastException: a Developer is not a Manager

IS, AS

      
Is

      
It checks whether the object is compatible with the specified type.

      
  • It checks the actual runtime type of the object.

      
It returns:

      
  • true
  • false

      
Example

      
Example

Employee emp = new Manager();

Console.WriteLine(emp is Employee);   // True
Console.WriteLine(emp is Manager);    // True
Console.WriteLine(emp is Developer);  // False

      

      
Visual Memory

Notice something important. The is operator does not check the reference type. It checks the actual object type.

      
Safe Down-casting

      
Example

if (emp is Manager)
{
    Manager mgr = (Manager)emp;
    mgr.ApproveLeave();
}

      

      
Now your application won't crash. If the object type is the same as the reference type then only it will allow.

      
Correction
is doesn't need the exact same type. It allows the cast when the object is that type or derived from it (or implements the interface). If SeniorManager : Manager, then emp is Manager is true for a SeniorManager.

      
Better Syntax (C# 7+)

      
Example

if (emp is Manager mgr)
{
    mgr.ApproveLeave();
}

      

      
This does two things:

      
  1. Checks whether emp is a Manager.
  2. Creates a Manager variable (mgr) if the check succeeds.

      
This is the syntax you'll often see in modern .NET code.

      
Real World example

      
Example

foreach (Employee e in employees)
{
    if (e is Manager m)
        m.ApproveLeave();
}

      

      
Only Manager objects will execute the method.


      
AS

      
It performs safe casting.

      
Instead of throwing an exception when the cast fails, it returns null.

      
Example

Employee emp = new Developer();
Manager mgr = emp as Manager;     // null, no exception

      

      
No exception. Your application continues running.

      
Example 1 (Successful Cast)

      
Example

Employee emp = new Manager();
Manager mgr = emp as Manager;     // mgr is NOT null
mgr.ApproveLeave();

      

      
Because the cast succeeded.

      
Why use as?

      
Suppose you're working with thousands of objects. You don't want your application to crash because one object isn't a Manager.

      
Instead:

      
Example

foreach (Employee e in employees)
{
    Manager m = e as Manager;
    if (m != null)
        m.ApproveLeave();
}

      

      
This is safe and clean.

      
Add
as works only with reference types and nullable value types. obj as int won't compile; obj as int? will.

Access Modifiers

      
It will define who can access the class, method, constructors, fields. This will provide security to classes and members.

      
  • public
  • private
  • protected
  • internal
  • protected internal
  • private protected


      
Try it

      
Who can touch Employee.Salary? Pick a modifier.

Public

      
Public members can be accessed from anywhere.

      
It doesn't matter if it's:

      
  • Same class ✅
  • Child class ✅
  • Different class ✅
  • Different project (assembly) ✅

      
Everyone can access it.

      
Q1: Can a public member be accessed from another project?

      
✅ Yes. If the class is public and the assembly is referenced, then a public member is accessible from another project.


      
Private

      
Private members can be accessed only within the same class.

      
Not by:

      
  • Child class ❌
  • Other class ❌
  • Other project ❌

      
Only the class that owns it.

      
Example

public class BankAccount
{
    private decimal balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentException("Invalid amount");
        balance += amount;
    }

    public decimal GetBalance() => balance;
}

var acc = new BankAccount();
acc.Deposit(500);        // ✓
// acc.balance = 1000000; // ✗ compile error, private

      

      
Now only the class controls how balance changes. This is a perfect example of Encapsulation.


      
Protected

      
A protected member can be accessed by the same class or derived(child) class.

      
✅ Inside the same class.

      
✅ Inside a derived (child) class.

      
❌ Not from other unrelated classes.

      
Example

      
Example

public class Employee
{
    protected decimal salary = 50000;
}

public class Manager : Employee
{
    public void ShowSalary() => Console.WriteLine(salary);   // ✓ child accesses protected
}

// Program.cs
Manager m = new Manager();
m.ShowSalary();          // ✓ works

      

      
This can be accessed. Because we are calling the public method of Manager (child). So salary is accessed by child class.

      
Program.cs calls → child Method → protected salary

      
But in this:

      
Example

// Program.cs
Manager m = new Manager();
Console.WriteLine(m.salary);   // ✗ compile error

      

      
The caller is Program, not Manager. The program is not inheriting from Employee.

An Internal member or class can be accessed only within the same assembly (Project).

      
Notes:

      
    
        
  • Namespace is used to organize code.
    • 
        
  • Assembly is the compiled output (.dll or .exe) and is what internal is based on.
    •

Example

{
    internal decimal CalculateSalary() => 50000;
}

      

      
In the same Project:

      
Project: EmployeeManagement.Business

      
Example

// Project: EmployeeManagement.Business

{
    public void Run() => new Employee().CalculateSalary();   // ✓
}

      

      
Works perfectly because both classes are in the same Project (Assembly).

      
In the Different Project:

      
Example

// Project: EmployeeManagement.Web  (references Business)
var emp = new Employee();
emp.CalculateSalary();     // ✗ compile error

      

      
Because CalculateSalary() is internal and not accessible.

Properties

      
Property provides controlled access to Data in class.

      
Example

public string Name { get; set; }

      

      
    
        
  • Name → Property
    • 
        
  • string → Property type
    • 
        
  • get → allows reading
    • 
        
  • set → allows assigning/changing
    • 
      

      
Usage

      
Example

Employee emp = new Employee();
emp.Name = "Asha";              // set
Console.WriteLine(emp.Name);    // get

      


      
Field vs Property

      
Public field

      
Example

public class Employee { public int Age; }
emp.Age = -50;      // nothing stops this

      

      
There is no built-in control between the caller and the field.

      
  • A field is a variable that stores data directly inside a class.

      
Property

      
Example

public class Employee
{
    private int age;                 // backing field (storage)
    public int Age                   // property (access mechanism)
    {
        get { return age; }
        set
        {
            if (value < 18) throw new ArgumentException("Age must be 18+");
            age = value;
        }
    }
}

      

      
This gives you a place to control how the value is read or changed. Here we will implement the strong encapsulation.

      
    
        
  • A property is not storage itself.
    • 
        
  • It is an access mechanism that reads from and writes to storage (typically a backing field).
    • 
      


      
Auto-Implemented Property

      
It provides the default logic. Like get set.

      
Example

public string Name { get; set; }

// the compiler generates roughly:
private string <Name>k__BackingField;
public string Name
{
    get { return <Name>k__BackingField; }
    set { <Name>k__BackingField = value; }
}

      

      
get defines how the property's value is read, while set defines how the property's value is assigned. An auto-property lets the compiler generate the backing field automatically, while still exposing the data through a property rather than directly exposing a field.

      
This is called an auto-implemented property.

      
You don't explicitly create the backing field.

      
The compiler creates a hidden backing field for you.


      
Read-Only Property

      
Now you can read the property, but you cannot normally assign it from outside the class.

      
Example

      
Example

public class Employee
{
    public int Id { get; }

    public Employee(int id)
    {
        Id = id;          // ✓ the constructor can initialize it
    }
}

var emp = new Employee(101);
// emp.Id = 200;      // ✗ compile error

      

      
This assigning the data will give a compile error.

      
But the constructor can initialize it.


      
Init-only property

      
We can initialize the value in the constructor using the property name. The advantage is readability.

      
A get-only property can typically be assigned inside the constructor. An init property can also be assigned during object initialization using an object initializer, but after the object has been created, it becomes read-only.

      
Example

public class Employee
{
    public int Id { get; init; }
    public string Name { get; init; }
    public string Dept { get; init; }
    public string Email { get; init; }
}

var emp = new Employee
{
    Id = 101,
    Name = "Asha",
    Dept = "IT",
    Email = "asha@corp.com"
};
// emp.Name = "Ravi";   // ✗ compile error, init window closed

      

      
Like this we can assign the value, when we have more properties.
