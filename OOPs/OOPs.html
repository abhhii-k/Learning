Class

A Class is a user-defined data type that acts as a blueprint for creating objects. It encapsulates data and behavior together.

A class can contain fields, properties, methods, constructors, events, and other members.

Memory for instance data is allocated only when an object is created.

Class Memory

When you create the class only MetaData loads.

After creating the object then only Memory in Heap will be allocated.

  • Fields
  • Properties
  • Constants
  • Methods
  • Constructors
  • Destructors (Finalizers)
  • Static Members
  • Nested Classes
  • Events
  • Indexers

Object

An object is an instance of a class, it represents a real-world entity and contains its own data (members or field) and behaviour (methods).

When you initialize the object using a new keyword, memory will be allocated in Heap.

Value types are not "always on the stack". They live wherever their container lives. A local int sits on the stack, but the int _id field above lives inside the object on the heap.

Difference Between Class and Object

A class is a blueprint or template that defines the structure and behavior of objects. It specifies what data and methods objects will have but doesn't store instance-specific data. An object is an instance of a class created using the new keyword. Each object has its own memory and maintains its own state while sharing the same class definition.

Declared onceCreated many times with new
Only metadata is loadedMemory allocated on the heap

Interview
Is string a value type?

No, it is a reference type. It is immutable, so every "change" creates a new string, which makes it behave like a value type when you assign and modify it.

Static

A static member belongs to the class itself, not to an object (instance).

Advantage is reusability. No data duplication.

Static members are stored in the static area (or Loader Heap).

Static field

A static member is a member belonging to a class rather than an instance of the class.

  • It is shared among the objects. So only one copy of this exists in memory.
  • A static member can access using the className without creating the object.

Example

Before:

Example · before 
public class Employee
{
    public string Name;
    public string Company = "Infosys";     // instance field
}

That means "Infosys" is duplicated in every object. Waste of memory.

Better Solution: Store it once.

Example · better solution 
public class Employee
{
    public string Name;
    public static string Company = "Infosys";   // one copy for the class
}

Console.WriteLine(Employee.Company);           // accessed with the class name
Static area · one copy
Employee (static)Company = "Infosys"
Heap · per object
Employee #1Name = "Asha" · no Company copy
Employee #2Name = "Ravi" · no Company copy

There is only one copy of: Company. No matter how many Employee objects you create.

Static Method

A static method belongs to the class rather than an instance. It can be called without creating an object and can directly access only static members of the class.

Note:

  • The static method can only access the static members. It can not access the non static member.
  • Only objects are able to access the non static method.
Correction

Precisely: a static method can't use instance members directly (it has no this). It can still use them through an object it receives or creates: static void Print(Employee e) => Console.WriteLine(e.Name);

Static constructor

A static constructor can not have access modifiers. It is always Private implicitly. Compilers enforce this.

Usage of static constructor

To initialize the static field.

Example 
public class Employee
{
    public static string Company;

    static Employee()                 // no access modifier, no parameters
    {
        Company = "Infosys";
        Console.WriteLine("Static ctor ran");
    }

    public Employee() { Console.WriteLine("Instance ctor ran"); }
}

new Employee();   // Static ctor ran, Instance ctor ran
new Employee();   // Instance ctor ran   (static ctor does NOT run again)

Who calls the Static Constructor?

✅ CLR (Common Language Runtime).

The CLR automatically executes the static constructor. Exactly once.

Before:

  • First object creation
  • OR first static member access

Whichever happens first.

Also remember

A static constructor takes no parameters, can't be overloaded, and can't be called by your code.

Static Class

A static class is a class that cannot be instantiated and can contain only static members. It is commonly used for utility or helper functionality, such as the built-in Math class.

Interview
Why is Main() static?

So the CLR can call the entry point without first creating an object of the class.

Can we overload static methods?

Yes. Overloading only needs a different parameter list. Static methods cannot be overridden, though.

Inheritance

Inheritance is a feature of an OOP that allows one class to acquire members of another class.

It promotes code reusability, maintainability and extensibility.

Example 
public class Employee  { public string Name; public void Work() { } }
public class Manager   : Employee { public void ApproveLeave() { } }
public class Developer : Employee { public void WriteCode() { } }

Manager m = new Manager();
m.Name = "Asha";      // inherited from Employee
m.Work();             // inherited from Employee
m.ApproveLeave();     // its own

Note: The child class can not inherit the Private members, static members and constructors.

Correction

Only constructors are truly not inherited. Private members are inherited (they exist inside the Manager object) but are not accessible from Manager's code. Public static members are reachable through the child too: Manager.Company works.

Base

Base is a keyword that helps to access the members (constructors, methods, properties, fields) of the immediate parent class.

Calling parent constructor

base() is used to call the constructor of the base class.

Example 
public class Employee
{
    public int Id;
    public Employee(int id) { Id = id; Console.WriteLine("Employee ctor"); }
}

public class Developer : Employee
{
    public Developer() : base(101)
    {
        Console.WriteLine("Developer ctor");
    }
}

Before executing the Developer constructor, call the Employee(int id) constructor with the value 101.

A child constructor can call only its immediate parent's constructor.

Calling parent method

If the parent and child class have the same method. But I need to call the parent class method. In this time we need to use the base keyword call the parent method.

Example 
public class Employee  { public virtual void Work() => Console.WriteLine("Employee working"); }
public class Developer : Employee
{
    public override void Work()
    {
        base.Work();                               // Employee working
        Console.WriteLine("Developer writing code");
    }
}

Calling parent properties

Example 
public class Employee  { public string Title { get; set; } = "Employee"; }
public class Developer : Employee
{
    public new string Title { get; set; } = "Developer";
    public void Show() => Console.WriteLine($"{Title} / {base.Title}");  // Developer / Employee
}

Accessing the parent field

Example 
public class Employee  { protected decimal Bonus = 5000; }
public class Developer : Employee
{
    private new decimal Bonus = 8000;
    public void Show() => Console.WriteLine($"{Bonus} / {base.Bonus}");  // 8000 / 5000
}

For code reusability and maintainability.

Encapsulation

It is the process of binding the data and methods together to protect the data. While restricting the direct access to data. In C# We can implement this using the Private fields and public properties or methods.

Example 
public class Employee
{
    private decimal _salary;                       // hidden data

    public decimal Salary                          // controlled access
    {
        get => _salary;
        set
        {
            if (value < 0) throw new ArgumentException("Salary cannot be negative");
            _salary = value;
        }
    }
}

var e = new Employee();
e.Salary = 50000;      // ✓
e.Salary = -10;        // ✗ throws, the class protects its data
// e._salary = -10;    // ✗ compile error, private

Interview Tip

A common follow-up question is:

If auto-implemented properties are public (public int Age { get; set; }), is that encapsulation?

The answer is:

  • Technically yes, because access still goes through a property rather than a field.
  • However, it doesn't provide much protection because there's no validation or restricted access.
  • Stronger encapsulation uses private fields with validation logic in the property setter when business rules need to be enforced.

Abstraction

Abstraction is the process of hiding the implementation and showing the only essential functionality to the user. Abstraction is mainly achieved using the abstract class and interface.

Advantage:

  • Hides complexity.
  • Improves maintainability.
  • Allows flexible implementations.
  • Lets users focus on functionality rather than implementation.

Interview Tip

Can we achieve Abstraction without using an abstract class?

Yes. We can achieve abstraction using interfaces as well. In fact, interfaces are often preferred when defining contracts because a class can implement multiple interfaces, whereas it can inherit from only one abstract class.

Does an abstract class have to contain an abstract method?

No. An abstract class can have zero or more abstract methods. Declaring a class as abstract simply means it cannot be instantiated directly.

Realtime Example and Advantage

Example · payroll 
public abstract class Employee
{
    public string Name;
    public abstract decimal CalculatePay();                  // WHAT, not HOW
    public void PrintPayslip() => Console.WriteLine($"{Name}: {CalculatePay()}");
}

public class Manager   : Employee { public override decimal CalculatePay() => 90000 + 15000; }
public class Developer : Employee { public override decimal CalculatePay() => 70000; }

public interface IReviewable { void Review(); }             // contract via interface

// var e = new Employee();   // ✗ abstract class can't be instantiated
Employee e = new Manager { Name = "Asha" };
e.PrintPayslip();          // payroll never knows how a Manager's pay is calculated

Advantage: payroll code calls CalculatePay() and stays the same when a new role is added.

Polymorphism

It is one of the four pillars of the OOPs, it allows the same method to behave differently based on the object by implementing the Method overloading (Compile-Time) and Method overriding (Run-Time).

Compile-Time polymorphism (Method overloading)

The compiler decides which method to call before the program runs. We can achieve this using the method overloading.

Method overloading is compile-time polymorphism. It means creating multiple methods with the same name in the same class but difference in the parameter list. The compiler decides which method to execute.

That's why it's also called as:

  • Compile-time Polymorphism
  • Static Polymorphism
  • Early Binding

Rules for Method Overloading

  1. Number of Parameters
  2. Type of Parameters
  3. Order of parameter
Example 
public class Payroll
{
    public void Pay(int id) { }                       // base version
    public void Pay(int id, decimal bonus) { }        // ✓ number of parameters
    public void Pay(string code) { }                  // ✓ type of parameters
    public void Pay(decimal bonus, int id) { }        // ✓ order of parameters
    // public int Pay(int id) { return 0; }           // ✗ return type alone: compile error
}
Add to the rules

Return type alone is not enough to overload. ref/out/in modifiers do count, but ref vs out alone does not.

Interview Tip

1. Can we overload static methods?

Answer

Yes. static int Add(int a, int b) and static double Add(double a, double b) can live together. Math.Max itself has many overloads.

2. Can constructors be overloaded?

Answer

Yes. Employee(), Employee(int id) and Employee(int id, string name) in one class is constructor overloading (see chapter 05).

3. Can methods be overloaded in different classes?

No. Method overloading is a concept within the same class.

Correction

Too strong. A derived class can add an overload of an inherited method: Employee.Work() plus Manager.Work(int hours), and both are callable on a Manager. Safer answer: "Normally within one class, but a derived class can add new overloads of inherited methods."

Method hiding

It is the process of hiding the parent class method in the child class. The child class declares a method with the same name and same parameters using the new keyword. Which method runs is decided by the reference type at compile time.

Example 
public class Employee { public void Work() => Console.WriteLine("Employee works"); }
public class Manager : Employee
{
    public new void Work() => Console.WriteLine("Manager works");
    public void ApproveLeave() { }
}

Employee emp = new Manager();
emp.Work();              // Employee works
// emp.ApproveLeave();   // ✗ not visible through an Employee reference

See in this reference is Employee but the object is Manager.

So the compiler decides what all members access this emp reference.

For the reference emp type is employee. So only employee members are accessible.

Runtime Polymorphism

Runtime polymorphism is method overriding. It allows the child class to provide its own implementation that is already defined in the base class.

We can achieve this using the base method marked as "virtual" and the child method marked as "override".

At the runtime CLR decides which method should executes based on the object.

Method Overriding (Virtual, override)

Example 
public class Employee { public virtual  void Work() => Console.WriteLine("Employee works"); }
public class Manager : Employee
{                       public override void Work() => Console.WriteLine("Manager works"); }

Employee emp = new Manager();
emp.Work();              // Manager works

In this still reference type is Employee and object is Manager.

Now the CLR says and This decision happens at runtime:

The reference is Employee, but the actual object is Manager. I'll execute the Manager's overridden method.

First, the compiler checks whether the method is virtual. If it is virtual, the compiler generates a virtual call.

The Secret of calling different method

Picture · the method table (vtable)
Employee method table
slot: Work()→ Employee.Work
Manager method table
slot: Work()→ Manager.Work (override replaced the slot)
  1. Every object on the heap carries a pointer to its own type's method table.
  2. emp.Work() is a virtual call, so at runtime the CLR follows emp → object → Manager's table.
  3. The Work() slot there points at Manager.Work, so that runs. With new instead of override, Manager gets a separate slot and the Employee slot still points at Employee.Work.

Interview

        
Can a constructor be private? Virtual? Static?
Private: yes (singleton, factory). Virtual: no, constructors are never virtual or inherited. Static: yes, but only one, with no parameters and no access modifier.

        
What happens if Dispose is not called?
The resource (DB connection, file handle) stays open until the GC eventually runs the finalizer, if there is one. Under load this exhausts the connection pool or locks files. That's why we always use using.

        
Finalize vs Dispose?
Dispose is deterministic and called by your code. Finalize is non-deterministic and called by the GC. The Dispose pattern uses both: Dispose does the work and calls GC.SuppressFinalize(this); the finalizer is only a backup for unmanaged resources.

The framework creates the object first and sets properties afterwards. EF Core and System.Text.Json can also use parameterized constructors when the parameter names match the properties.

New lesson

Why seal?

      
    
        
  • Design intent: the class was not built to be extended, so nobody can break it by overriding.
    • 
        
  • Security: stop someone changing the behaviour of sensitive logic (validation, pricing).
    • 
        
  • Performance: the JIT can call methods directly instead of through the vtable (devirtualization).

Can we create an object of a sealed class?
Yes. Sealed only blocks inheritance, not instantiation. (A static class blocks both.)

        
Can we seal a method that is not an override?
No. sealed on a method is only allowed together with override. A non-virtual method can't be overridden anyway.

        
Can a class be both abstract and sealed?
No, they contradict each other: abstract must be inherited, sealed can't be. Internally, a static class is compiled as abstract + sealed, but you can't write that yourself.

        
sealed vs private constructor vs static class?
sealed: objects allowed, inheritance blocked. Private constructor: no outside new, and inheritance blocked in practice. Static class: no objects and no inheritance, only static members.

Which one should I pick?

      

        
Abstract class when
The classes are closely related (Manager, Developer are all Employees) and share real code or state, such as Name or CalculateTax().

        
Interface when
You define a capability that unrelated classes can have (IPayable for Employee and Vendor), you need multiple inheritance, or you want to inject and mock it (IEmployeeRepository).

      

      
In real ASP.NET Core projects you use interfaces far more often, because DI and unit testing are built around them. A common pattern combines both: an interface for the contract, and an abstract base class implementing it to share code.


      
Multiple interface inheritance

public interface ILeader   { void Lead(); }

    public void Lead() { }

    void ISmsNotifier.Send()   => Console.WriteLine("SMS");

Modern C# (8+): default interface methods


public interface ILogger
{
    void Log(string msg);
    void LogError(string msg) => Log("ERROR: " + msg);   // body inside the interface
}

Interview

        
Why use an interface instead of an abstract class?
A class can implement many interfaces but inherit one class; interfaces keep coupling loose, so they are what we inject with DI and mock in unit tests; and unrelated types (even structs) can share them. Use an abstract class when related classes need shared code or state.

        
Can an abstract class have a constructor? Why, if you can't create it?
Yes. It runs when a derived object is created (through base(...)) to initialise the shared fields. Make it protected.

        
Can an abstract class implement an interface without implementing its methods?
Yes. It can declare them abstract and leave them to the derived class.

        
After default interface methods, is there any difference left?
Yes: interfaces still have no instance fields, no constructors, and no protected state, and a class can still inherit only one class. The IS-A vs CAN-DO design difference stays the same.

Interview

        
Why must GetHashCode be overridden when Equals is?
Hash-based collections use GetHashCode to find the bucket and Equals to confirm. If equal objects return different hash codes, they land in different buckets, so lookups fail and duplicates appear.

        
Can two different objects have the same hash code?
Yes, that is a collision and it's allowed. Equal objects must have equal hash codes, but equal hash codes don't mean equal objects.

        
Difference between Equals and ReferenceEquals?
Equals is virtual and can be overridden for value equality. ReferenceEquals is static and always checks if both references point to the same object.

        
How does a struct compare with Equals by default?
ValueType.Equals compares all fields, using reflection when it must, which is slow. Override Equals (or implement IEquatable<T>) on structs used heavily in comparisons.

An object with no class name. The compiler creates the class for you.

Anonymous types: method-local, read-only, great in LINQ. Tuples (int Id, string Name): lightweight value types you can return from methods. Records: named types with value equality, for DTOs shared across the app.

New lesson

      
These describe how two objects are connected. They go from loose to strong: uses → has → owns.

ManagerLeaveRequest
uses / knows. Both live independently.

UML symbols: plain line = association, hollow diamond ◇ = aggregation, filled diamond ◆ = composition (the diamond sits on the "whole" side).


      
1. Association: "uses"

      
Two objects work together, but neither owns the other. Often the other object just arrives as a method parameter.


public class Manager : Employee
{
    public void Approve(LeaveRequest request)     // Manager USES a LeaveRequest
    {
        request.Status = "Approved";
    }
}
// The request existed before the call and still exists after it.


      
2. Aggregation: "has-a" (weak)

      
A whole that holds parts, but the parts are created outside and can live on their own.


public class Department
{
    public string Name { get; }
    public List<Employee> Employees { get; } = new();

    public Department(string name) => Name = name;
    public void Add(Employee e) => Employees.Add(e);   // employee passed IN
}

var asha = new Employee(101, "Asha");
var it = new Department("IT");
it.Add(asha);
it = null;          // department gone, Asha still exists and can join another department


      
3. Composition: "owns-a" (strong)

      
The whole creates the part itself and never shares it. When the whole goes, the part goes too.


public class Employee
{
    private readonly IdCard _idCard;               // owned

    public Employee(int id, string name)
    {
        _idCard = new IdCard(id);                  // created INSIDE
    }
}
// No IdCard exists without its Employee. When the Employee is collected,
// nothing else references the IdCard, so it is collected too.

Interview

        
Give a real project example of each.

How does C# enforce composition if the GC frees memory?
Through design, not keywords: the whole creates the part privately and never exposes or shares it. Then nothing else references the part, so it is collected with the whole. If the part holds resources, the whole disposes it in its own Dispose.

Composition vs Inheritance
New lesson

      
Inheritance = IS-A. A Manager is an Employee. Composition = HAS-A. An Employee has a pay calculator. The well-known advice is "favour composition over inheritance".


      
The problem with inheritance everywhere


class Employee { }
class FullTimeEmployee           : Employee { }   // pay rule
class ContractEmployee           : Employee { }
class RemoteFullTimeEmployee     : FullTimeEmployee { }   // + location rule
class RemoteContractEmployee     : ContractEmployee { }
class RemoteContractEmployeeWithShiftAllowance : RemoteContractEmployee { }   // 😬
// every new combination = a new class. Changing Employee can break all of them.

      
    
        
  • Class explosion: each combination of behaviours needs its own subclass.
    • 
        
  • Tight coupling / fragile base class: a change in Employee ripples into every child.
    • 
        
  • Fixed at compile time: an employee can't switch from contract to full-time at runtime.
    • 
        
  • Only one parent in C#, so you can't mix two bases.
    • 
      


      
The same thing with composition


public interface IPayPolicy      { decimal Calculate(decimal baseSalary); }
public interface ILocationPolicy { decimal Allowance(); }

public class FullTimePay : IPayPolicy { public decimal Calculate(decimal b) => b; }
public class ContractPay : IPayPolicy { public decimal Calculate(decimal b) => b * 1.2m; }
public class RemoteWork  : ILocationPolicy { public decimal Allowance() => 2000; }
public class OfficeWork  : ILocationPolicy { public decimal Allowance() => 0; }

public class Employee
{
    private IPayPolicy _pay;                 // HAS-A
    private readonly ILocationPolicy _location;

    public Employee(IPayPolicy pay, ILocationPolicy location)
    {
        _pay = pay;
        _location = location;
    }

    public decimal MonthlyPay(decimal baseSalary) =>
        _pay.Calculate(baseSalary) + _location.Allowance();

    public void ConvertToFullTime() => _pay = new FullTimePay();   // swap at runtime
}

var e = new Employee(new ContractPay(), new RemoteWork());   // any combination, no new class


      

        
Inheritance (IS-A)Composition (HAS-A)

        
          
RelationshipManager is an EmployeeEmployee has an IPayPolicy

          
CouplingTight: child depends on parent's internalsLoose: depends on an interface

          
FlexibilityFixed at compile timeSwap parts at runtime

          
ReuseWhite-box (child sees protected members)Black-box (only the public contract)

          
TestingHarder: must deal with the base classEasy: inject a fake IPayPolicy

          
PolymorphismThrough virtual/overrideThrough interfaces

        
      

      
When inheritance is still right
When the IS-A is true in every situation, the child can be used anywhere the parent is (Liskov, chapter 21), and you really want to share code. Framework examples: ControllerBase, DbContext, Exception.

      
Interview

        
Why favour composition over inheritance?
It avoids class explosion and fragile base classes, keeps classes loosely coupled through interfaces, lets you change behaviour at runtime, and makes unit testing easy because collaborators can be mocked. It's also exactly how DI works in ASP.NET Core.

        
How do you decide between them?
Say the sentence out loud. "Manager is an Employee" → inheritance. "Employee has a pay policy" → composition. If the "is-a" is only true sometimes, or you're inheriting just to reuse a method, use composition.

SOLID Principles
New lesson

      
Five design rules that keep code easy to change. For 4+ years of experience, expect to explain each with a problem → fix from your own projects.

SSingle Responsibility Principle (SRP)

        
A class should have only one reason to change.

        

          
✗ Violates


public class EmployeeService
{
    public decimal CalculateSalary(Employee e) { ... }   // payroll rules
    public void Save(Employee e) { ... }                 // SQL
    public void SendPayslipEmail(Employee e) { ... }     // SMTP
}
// changes to tax rules, DB, or email all edit this class

          
✓ Follows


public class SalaryCalculator   { public decimal Calculate(Employee e) { ... } }
public class EmployeeRepository { public void Save(Employee e) { ... } }
public class PayslipEmailer     { public void Send(Employee e) { ... } }
// each class has one job and one reason to change

        

        
Say it: "Each class does one job. In my API, controllers only handle HTTP, services hold business logic, and repositories talk to the database."

      


      

        
OOpen/Closed Principle (OCP)

        
Open for extension, closed for modification. Add new behaviour by adding code, not by editing working code.

        

          
✗ Violates


public decimal Bonus(Employee e)
{
    if (e.Type == "Manager")   return e.Salary * 0.20m;
    if (e.Type == "Developer") return e.Salary * 0.10m;
    // new role "Tester"? edit this method again...
    return 0;
}

          
✓ Follows


public abstract class Employee
{
    public decimal Salary { get; set; }
    public abstract decimal Bonus();
}
public class Manager   : Employee { public override decimal Bonus() => Salary * 0.20m; }
public class Developer : Employee { public override decimal Bonus() => Salary * 0.10m; }
public class Tester    : Employee { public override decimal Bonus() => Salary * 0.08m; }  // just add

        

        
Say it: "Instead of growing if/switch chains, I use polymorphism or the Strategy pattern, so a new case is a new class. ASP.NET Core middleware and filters work this way too."

      


      

        
LLiskov Substitution Principle (LSP)

        
A child class must be usable anywhere its parent is expected, without surprises.

        

          
✗ Violates


public class Employee

    public virtual int PaidLeaveDays() => 24;
}
public class Contractor : Employee
{

        throw new NotSupportedException();   // surprise!
}

foreach (Employee e in staff)
    total += e.PaidLeaveDays();              // crashes on a Contractor

public class Employee   : Worker, IHasPaidLeave { public int PaidLeaveDays() => 24; }

    total += e.PaidLeaveDays();

Don't force a class to implement methods it doesn't use. Prefer small, focused interfaces.

Which SOLID principle have you applied most, and how?

Dependency Injection
New lesson

      
Instead of a class creating the objects it needs with new, they are given to it from outside, usually through the constructor. ASP.NET Core has a DI container built in.


      

        

          
Without DI


public class EmployeesController : ControllerBase
{
    private readonly EmployeeService _service = new EmployeeService(
        new SqlEmployeeRepository("Server=..."));   // builds its own dependencies

    // tightly coupled, connection string inside,
    // impossible to unit test without a database
}

        

        

          
With DI (constructor injection)


public class EmployeesController : ControllerBase
{
    private readonly IEmployeeService _service;

    public EmployeesController(IEmployeeService service)
    {
        _service = service;          // the container passes it in
    }

    [HttpGet]
    public IActionResult Get() => Ok(_service.GetAll());
}

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IEmployeeRepository, EmployeeRepository>();
builder.Services.AddScoped<IEmployeeService, EmployeeService>();
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();

var app = builder.Build();

  2. It looks up the registration: IEmployeeService → EmployeeService.
    3. 
        
  3. EmployeeService needs an IEmployeeRepository, so the container builds that first.
    4. 
        
  4. It creates the objects bottom-up, injects them, and disposes scoped ones when the request ends.
    5.

Lightweight, stateless helpers: email builder, mappers.

DbContext, repositories, unit of work, per-request user info.

One object for the whole app, shared by every request and thread.

Classic trap: captive dependency
Never inject a Scoped service (like DbContext) into a Singleton. The singleton lives forever, so it keeps the first request's DbContext alive and shares it across threads, which causes stale data and concurrency errors. In Development, ASP.NET Core throws "Cannot consume scoped service from singleton". Rule: a service may depend only on services that live as long or longer than itself.

Why it matters: unit testing

Interview

        
When would you use Scoped instead of Singleton?
When the service holds per-request state or isn't thread-safe, like DbContext or a repository using it. Singleton is for stateless or thread-safe shared things like configuration or a cache.

        
DI vs IoC vs DIP?
DIP: the principle, depend on abstractions. IoC: the idea that something else controls object creation and flow. DI: the concrete technique, where dependencies are passed in, usually by a container.

        
What happens if two implementations are registered for the same interface?
Constructor injection of IEmailSender gets the last one registered. Inject IEnumerable<IEmailSender> to get all of them. .NET 8 added keyed services (AddKeyedScoped) to pick one by key.

        
How do you use a scoped service inside a singleton or background service?
Inject IServiceScopeFactory, create a scope with using var scope = factory.CreateScope(), and resolve the scoped service from scope.ServiceProvider.
